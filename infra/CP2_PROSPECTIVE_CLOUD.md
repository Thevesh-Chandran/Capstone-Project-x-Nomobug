# CP2 prospective cloud collector

The daily `cp2-reporting-daily` job and the time-sensitive model experiment are separate. The private Cloud Run service `cp2-prospective-collector` is called by `cp2-prospective-every2m` in `asia-southeast1`. The local Windows collector remains disabled. The service uses the same frozen v5 bundle and five-minute post-service logging rule. It never backfills a prediction. Its source Google OAuth secret has only read-only Calendar and Sheets scopes.

The collector checks Calendar on each tick. When a paid service is near its scheduled end, it reads fresh Sheets/Calendar data, obtains prior weather, derives predictors in bounded temporary BigQuery queries, rechecks the Calendar event, and writes an immutable private receipt before acknowledging the score. The `audit.prospective_predictions` table is a restricted index of receipt hashes and risk probabilities; the full source-linked receipt is in `gs://profound-keel-500007-s4-cp2-prospective/prospective_logs/`. Neither is a dashboard source. The bucket also holds the exact private model and reference snapshot, checked against `config/cp2_cloud_artifacts.json` and the frozen model registry. The container contains code and public configuration only.

## Verify and recover

Check Scheduler state, Cloud Run request status, and `state/last_tick.json` in the private bucket. A healthy idle tick has HTTP 200 and an advancing `checked_at_utc`. `missed_event_windows` is cumulative; it must never decrease because a late score was fabricated. The separate `state/full_smoke.json` confirms a full source-to-model cloud run. A successful idle tick alone does not prove that a real service-end score can meet the five-minute gate.

If refresh or source access fails, pause `cp2-prospective-every2m`, inspect only error types and private run evidence, correct the fault, and manually verify a cloud tick before resuming. The Cloud Storage generation precondition prevents a second receipt for the same anchor. A cross-run lease prevents overlap; a worker terminates itself before 18 minutes, and another worker can recover a lease older than 22 minutes. BigQuery indexing reconciles from durable receipts after a partial failure. A service whose five-minute window expires remains a missed window.

Do not describe a declared cohort as complete until every eligible service has one timely receipt. The original 28 September cohort already has 20 missed windows. The 30 September–27 October repaired protocol was declared before its start; retain that exact protocol only if hosted collection and a full cloud smoke test are verified before 30 September. Otherwise declare a later full-day cohort before using its predictions for a new test. Complete 30-day outcomes are required before any one-time future accuracy report. The October submission can use the historical held-out test without claiming future accuracy.

Cloud Run is private and only the dedicated scheduler identity has `run.invoker`. The collector runtime identity has BigQuery job creation, project-level **read-only** BigQuery data access, audit dataset write access, bucket object access, and access to the three approved Google source secrets. The project-level reader is needed because each daily reporting release creates new candidate datasets behind stable Silver/Gold views; a grant on only today's candidate dataset failed the full smoke test. Narrow this role only after release automation grants read access to every newly published candidate before pointer promotion. Review [Cloud Run scheduling](https://docs.cloud.google.com/run/docs/triggering/using-scheduler), [request timeout behavior](https://docs.cloud.google.com/run/docs/configuring/request-timeout), and [private bucket access](https://docs.cloud.google.com/storage/docs/public-access-prevention) when changing this deployment.
