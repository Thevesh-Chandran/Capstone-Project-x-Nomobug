# CP2 reporting job runbook

The daily batch runs `python -m scripts.cp2_reporting_release run` in one Cloud Run Job task at **06:00 Asia/Kuala_Lumpur**. It reads the approved Google Sheets and Calendar sources through an OAuth refresh token with only `spreadsheets.readonly` and `calendar.readonly`, snapshots Bronze, builds candidate dbt Silver/Gold, validates KPIs, then publishes. The local two-minute prospective collector is a separate Windows task through 27 October; the cloud batch does not replace it or retrain the frozen v5 model.

The Cloud Run Job uses one task, parallelism one, 20-minute timeout, zero automatic task retries, 1 vCPU and 2 GiB. Each dbt and validation query has a 100 MiB billed-bytes ceiling in the project configuration. Cloud Scheduler also has zero retries. These are per-execution limits; **RM 30/month is an operator stop-work ceiling**, not a guarantee that Google cannot charge more. [Ordinary budgets alert but do not stop spend](https://docs.cloud.google.com/billing/docs/how-to/budgets). A [Cloud Run spend cap](https://docs.cloud.google.com/billing/docs/how-to/budgets-spend-caps) may be available in Billing console preview; it covers Cloud Run only, can enforce late, and does not cap BigQuery, Scheduler, Secret Manager, or Artifact Registry.

## One-time setup

1. In Cloud Billing Reports, filter to project `profound-keel-500007-s4`, current month, and record the current **MYR** total and UTC observation time. Stop if it is RM 30 or more. Check this before each deployment and daily while the schedule is active in October. The billing account uses MYR, but reported costs can lag.
2. From the repository root, run `pwsh -File infra/bootstrap_cp2.ps1` to preview. To apply, use `pwsh -File infra/bootstrap_cp2.ps1 -Apply -ObservedProjectSpendMYR 0.00 -ObservedAtUtc 2026-09-28T10:00:00Z`, replacing both observed values. It first creates/verifies a **project-scoped monthly RM 30 budget** with 50%, 80%, and 100% alert emails, then enables only required APIs and creates scoped identities, secrets without versions, Artifact Registry, and GitHub Workload Identity Federation. If budget creation or permission checks fail, inspect the error and stop. Do not bypass the budget gate.
3. Upload only the three ignored, approved local JSON files with `pwsh -File infra/seed_cp2_secrets.ps1 -TokenPath secrets/google_token.json -SourceIdsPath secrets/google_source_ids.json -MetadataPath data/profiles/google_source_metadata.json -Apply`. The script checks the exact two read-only OAuth scopes and never prints secret values. It refuses duplicate versions without `-Rotate`.
4. Configure the GitHub `cp2-production` environment for reviewers or branch protection. The `Deploy CP2 reporting job` workflow is also manually triggered, restricted to the numeric repository ID and `main`, and uses a keyless GitHub OIDC provider with a condition on owner ID, repository ID, branch, and manual dispatch. Enter a fresh project Billing Reports cost and observation time when dispatching. The deploy identity intentionally cannot read Billing, so this operator observation is the spend gate; repeat it before each dispatch. The workflow runs Python/dbt checks, builds and smoke-tests the Docker image, pushes a commit-SHA image, and deploys the bounded job. It does not execute unless `run_after_deploy` is checked.
5. Execute a manual cloud run and check the [audit table](#run-and-recovery). Only after that passes, create the schedule with `pwsh -File infra/schedule_cp2.ps1 -Apply`; this initially leaves it paused. Then run `pwsh -File infra/schedule_cp2.ps1 -Apply -Activate`. Verify one 06:00 MYT scheduled run in Cloud Scheduler, Cloud Run executions, and BigQuery audit.

The runtime service account can create candidate datasets and jobs, write the existing Bronze/Silver/Gold/audit datasets, and read only quality/analytics_ml. It has `secretAccessor` on the three CP2 secrets. The scheduler identity has `run.invoker` only on this job. The deploy identity can deploy Run jobs, push to the CP2 image repository, and act as the runtime identity. No service-account key is created. Runtime source files are mounted as separate Secret Manager volumes at `/var/run/secrets/`; they, customer data, local `.env`, and `outputs/` are excluded from the Docker context and Git.

## Run and recovery

For a manual run: `gcloud run jobs execute cp2-reporting-daily --project profound-keel-500007-s4 --region asia-southeast1 --wait`. Verify the latest status in `audit.release_runs` using the query below with `--maximum_bytes_billed=104857600` and check a dashboard freshness value. The audit rows contain run IDs, status, timestamps, and snapshot table IDs; customer rows belong only in restricted Bronze and local ignored output. `PUBLISHED` is a successful release; `FAILED` preserves the previous published views unless a promotion rollback also failed. Inspect the typed error and Cloud Run execution logs without copying private content into GitHub issues or chat.

```powershell
bq query --project_id=profound-keel-500007-s4 --location=asia-southeast1 --use_legacy_sql=false --maximum_bytes_billed=104857600 'SELECT run_id, event_at, status, error_type FROM `profound-keel-500007-s4.audit.release_runs` ORDER BY event_at DESC LIMIT 20'
```

If a run fails, **pause the scheduler**, inspect its run ID and last successful audit entry, fix the source/IAM/schema fault, recheck current spending, and manually execute the job once. Resume only after validation passes. If a published release needs rollback, use the reporting release's BigQuery-backed rollback command with its run ID; verify the current Gold view pointers and audit status before resuming. Do not delete immutable Bronze snapshots or candidate datasets as a recovery shortcut. Cloud Scheduler's `jobs.run` request only starts a Run execution; its HTTP success does **not** prove the batch completed. Always inspect the Run execution and audit status.

```powershell
gcloud scheduler jobs pause cp2-reporting-daily-trigger --project profound-keel-500007-s4 --location asia-southeast1
gcloud run jobs executions list --job cp2-reporting-daily --project profound-keel-500007-s4 --region asia-southeast1
gcloud scheduler jobs resume cp2-reporting-daily-trigger --project profound-keel-500007-s4 --location asia-southeast1
```

The latest cloud audit run, not the local `outputs/` directory, is the durable last-success record. Cloud Run's filesystem is ephemeral. The exact release and rollback behavior is specified in [`scripts/cp2_reporting_release.py`](../scripts/cp2_reporting_release.py), while the existing collector and prospective logs stay local.
